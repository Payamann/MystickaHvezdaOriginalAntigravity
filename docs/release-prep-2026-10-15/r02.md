# R02 — trvalé doručení osobní mapy

Lokální kandidát; dne 16. 10. 2026 proběhla samostatná read-only kontrola produkčního schema přes Supabase MCP projekt `dybfmdtmmocrjbdfbxbb` (Mystická Hvězda), bez čtení zákaznických řádků a bez mutací. Implementace a níže uvedené testy jsou připravené pro společný závěrečný průchod. V tomto kroku nebyl spuštěn test, build ani prohlížeč.

## Změna

- Nová objednávka mapy dostává serverový stav `personalMapFulfillment: {version: 1, state: pending}` v existujícím soukromém JSONB payloadu. Před generováním se atomicky zapíše claim s UUID revizí. Dva procesy nemohou současně získat stejnou revizi; v jednom procesu sdílejí promise.
- Vytvořené sekce se ukládají před renderem. Render selže → nový pokus používá stejné sekce. Připravený e-mail včetně přesných PDF bytů v base64, HTML, příjemce a hlaviček se uloží před prvním odesláním. Opakování neregeneruje text ani přílohu a nezávisí na pozdější změně šablony.
- Odesílání používá `personal-map-${orderId}`. Čas prvního pokusu se uloží před voláním poskytovatele, ID přijaté zprávy do existujícího `email_id`. Uložené ID umožňuje jen dokončit finální stav objednávky bez dalšího sendu.
- Neúspěch zápisu receipt i finálního `fulfilled` je výslovná chyba. Ztracená odpověď / receipt zápis používá přesně stejný request a klíč. Po 23 hodinách od prvního pokusu automatické odesílání končí a vzniká provozní alert k ruční kontrole; nedojde k novému sendu po vypršení 24hodinové idempotence Resend.
- Pokud generování prokazatelně vrátí chybu, claim se uvolní a další pokus může generování zopakovat. Úspěšné generování následované neúspěšným uložením nebo přerušením procesu se automaticky neopakuje. Po 20 minutách vyžaduje kontrolu a alert. Již uložený výsledek se nikdy nevymění za nový.
- Produkční chyba AI už nevrací obecnou náhradní mapu jako splněný placený výklad. Existující syntetický režim `NODE_ENV=test` / `MOCK_AI` zůstává pro testování.
- Webhook i reconciliation předávají ID objednávky; služba vždy načítá trvalý vstup. Cena, poskytovatelé, modelové rozpočty a kontrola plateb se nemění. Změna se netýká ročního horoskopu ani vztahového výkladu.

## Migrace, soukromí a omezení

Read-only schema kontrola potvrdila, že `public.one_time_order_inputs` má `payload jsonb NOT NULL`, `email_id text` nullable, `email_sent_at timestamptz` nullable, `status text NOT NULL`, `stripe_session_id text` nullable a `fulfilled_at timestamptz` nullable. Potvrdila také RLS `enabled=true` pro `one_time_order_inputs` i `one_time_purchases` s policy `No direct access` (`ALL`, `USING false`, `WITH CHECK false`), partial unique index `one_time_order_email_id_unique` na nenulový `email_id`, unique `stripe_session_id` a BEFORE UPDATE trigger `preserve_one_time_email_id` se stejným názvem funkce. Žádné zákaznické řádky nebyly čteny a žádná mutace nebyla provedena.

Nová SQL migrace proto podle tohoto ověření není potřebná. Sloupce receipt a ochranu neměnného provider ID už definuje `server/scripts/sql/relationship-email-delivery.sql`; jejich reálný PostgREST/SQL CAS zápis, souběh a chování po restartu produkčního procesu zůstávají netestované. Nová data se nepřidávají do veřejného endpointu ani do Stripe metadat. Existující retenční úklid smaže payload spolu s objednávkou.

CAS filtr používá pouze vnořenou UUID revizi, nikoli celý JSON/PDF v URL. PDF je uložené v DB jako součást payloadu: zvyšuje velikost řádku a čtení objednávky, ale nevyžaduje nový storage bucket a jeho oprávnění. Přijetí poskytovatelem není potvrzené doručení do schránky.

Starší nevyřízená mapa bez nového serverového stavu se automaticky negeneruje. Starý kód mohl úspěšně odeslat e-mail a nezapsat ani failure/receipt, takže nulový retry_count neprokazuje, že nebyla odeslána. Taková objednávka vyvolá alert pro provozní kontrolu. Již splněné objednávky nebo uložené provider ID jsou no-op. Před případným ručním nastavením `pending` je nutné potvrdit platbu i absenci předchozího odeslání; pokud poskytovatel odeslání potvrdí, doplnit jeho receipt a dokončit stav, neposílat znovu. Hromadný backfill se nepřipravuje ani nespouští.

Pád procesu mezi úspěšným generováním a jeho uložením nelze bez transakční podpory externího generátoru automaticky obnovit se stejným nezapsaným výsledkem. Zvolený postup chrání před tichým druhým generováním a předává tuto vzácnou chybu k ruční obnově. Běžný výpadek rendereru nebo e-mailu zůstává automaticky obnovitelný z uloženého obsahu.

## Připravené závěrečné ověření

- `server/tests/personal-map-fulfillment.test.js`: restart/final-state failure, receipt write failure, shodný request a klíč, timeout/23h, selhání renderu, selhání uložení PDF i generovaného výsledku, uvolnění prokazatelně selhaného generování, souběžné procesy a bezpečné zastavení starší objednávky.
- `server/tests/personal-map-generation-failure.test.js`: produkční větev při mockované chybě AI nevrací fallback.
- Doplněný `server/tests/email-service.test.js`: přesný uložený payload a idempotency key předané Resend adaptéru.
- Navazující existující sady: `one-time-orders.test.js`, `one-time-order-reconciliation.test.js`, `personal-map-pdf.test.js`, `stripe.test.js`, `payment-checkout.test.js`, `rocni-horoskop.test.js`.

Jednotkové CAS testy mají lokální model databáze; ani po read-only ověření schema nejsou důkazem skutečného PostgREST/SQL CAS zápisu, souběhu nebo restart recovery. Neověřují ani reálné doručení e-mailu a rozhodnutí nad starými nejasnými objednávkami. R02 proto není tímto dokumentem označeno za hotové.

Dokumentace kontrolovaná při přípravě: [Supabase update](https://supabase.com/docs/reference/javascript/update), [Resend idempotency keys](https://resend.com/docs/dashboard/emails/idempotency-keys).
